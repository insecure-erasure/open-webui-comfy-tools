# Design Notes — Migration to Rich UI (open-webui-comfy-tools)

## Common pattern (all tools)

- Return `(HTMLResponse, context)` with the `Content-Disposition: inline` header.
- The Open WebUI middleware detects the `HTMLResponse`, emits the `embeds` event via Socket.IO, and the frontend renders it as a **sandboxed** iframe.
- The LLM **never sees the HTML**; it only receives the `context`.
- **Eliminates**: (a) context contamination (the `image_md` strings / HTML blocks no longer enter the LLM's context) and (b) the dependency on the agent reproducing the Markdown/HTML in its response (rendering becomes deterministic, via middleware + frontend).
- **Retained**: chaining still depends on the agent reading the `context` and passing it to the next tool (necessary and inevitable).
- **Security**: `allowSameOrigin` **OFF** (default). Decision made because third-party tools with embeds will be used; enabling it would give any embed access to the session/DOM of the chat. The only "loss" is not being able to read the exact Open WebUI theme.
- **Light/dark theme** in embeds: via `prefers-color-scheme` (detects the browser/system). Self-contained, without same-origin. Assumed limitation: it does not match the Open WebUI theme if it differs from the system.

## 1. smart_generate_image / edit_image / enhance_image
*(Image tools with viewer)*

- **`context`**: `{ "image": <url> }` — a single actionable value (the **URL**), ready for the `image` parameter of the downstream tools. The LLM needs nothing more.
- **Embed**: self-contained image viewer.
  - Width: fit to the chat container.
  - Height: **capped at 70vh** maximum, centered (flexbox), `object-fit: contain` (no distortion).
  - The backend **does not measure** the image; the aspect ratio is known a priori (`reduced_w:reduced_h`), useful for aspect reservation and avoiding the "jump" on load.
- **Modal viewer (lightbox) replicated inside the iframe**:
  - Open: a click on the thumbnail.
  - Zoom: image **fit to screen** (no scroll).
  - Close: X in the **top-left corner**.
  - Download: real button in the **top-right corner** (**forced download**, regardless of how ComfyUI serves the file).
  - **Appearance**: standard lightbox, **no exact replica** — full-screen overlay, dark/semi-transparent background, "floating" buttons over the image, `prefers-color-scheme`.
- **Chains**: yes (to the other tools). That is why the `context` is actionable.

---

## 2. virtual_try_on
*(Image tool with viewer + extra data)*

- **`context`**: `{ "image": <url>, "prompt": <text> }` — same base as the image tools, **plus the `prompt`** generated by the workflow (via `_extract_text`), which the agent uses to reply to the user. It is the only justified exception to the minimal `context`.
- **Embed**: identical to the image viewer (70vh max, centered, lightbox with zoom/close/download, `prefers-color-scheme`).
- **Chains**: yes (its result can be reused), same as the image tools.

---

## 3. compare_images
*(Interactive slider — terminal result)*

- **`context`**: **empty**. It is a terminal result: it does not chain with another tool. The LLM only needs to know that the comparison was shown (it will receive the middleware's generic message).
- **Embed**: interactive before/after slider.
  - **Width**: **maximum available** (100% of the chat container). It is a horizontal component; it must use the full width.
  - Height: resulting from the aspect ratio, via `reportHeight()`.
  - No thumbnail centering: it fills the width (unlike the image viewer).
- **Requires two valid URLs** (validated with `urlparse`). This is the reason the image tools emit a **URL** (and not a filename) in their `context`.
- **Adaptive sizing** (maintainer decision, 2026-08-04): on **vertical/portrait** devices the slider fills the full width with **no height cap**; on **horizontal/landscape** devices the height is **capped at 80% of the available vertical space**, width scaled proportionally and centered. The available height is approximated with the device screen (`screen.availHeight`) because the sandboxed iframe cannot read the parent viewport (cross-origin, `allowSameOrigin` OFF). Orientation detection is conservative: `screen.orientation` when available, then `window.orientation`, then a width/height comparison; degenerate screen values (e.g. 0-height in webviews) or any ambiguity are treated as portrait so the cap can never fire on a portrait device (fix for the reported mobile reduction).
- **Repo status**: the code in master **still uses the hack** (HTML block + instruction to the agent), but the README **already documents the Rich UI version** — there is an inconsistency. The migration would align the code with the README.
- **Does not require** ComfyUI or a workflow (it receives two URLs).
- **Chains**: no.

---

## 4. generate_video
*(Video player — terminal result)*

- **`context`**: **empty**. Terminal result: the video is not reused as input to another tool. The LLM only needs to know that it was generated and shown.
- **Embed**: `<video>` element (with `autoplay`, `muted`, `loop` — keep `muted` so autoplay works, since browsers block autoplay with sound).
- **Width**: maximum available.
- **Chains**: no.
- The migration here is especially valuable: the current hack (reproducing a complex `<video>` block) is the most fragile of all, with more risk of losing attributes / breaking HTML.

## 5. Extension to tools that return an image (general rule)

Any tool in the repo (current or future) that returns a **generated image** that can be reused must follow the **same pattern as `smart_generate_image`**:

- Return `(HTMLResponse, context)` with `Content-Disposition: inline`.
- **Actionable `context`**: `{ "image": <url> }` — the **URL** as the single value.
- **Embed**: image viewer (70vh max, centered, lightbox with zoom/close/download, `prefers-color-scheme`).
- **`context` decision rule**:
  - If the result **is reused** as input to another tool → actionable `context` (with the URL).
  - If the result is **terminal** (only shown to the user) → empty `context`.

### Why the URL is the single value (not the filename)

- **The comparator (`compare_images`) requires it**: it needs **two valid URLs**. Returning filenames would force converting filename→URL in the comparator, complicating its logic. With URLs, there is no conversion.
- **Uniformity**: all downstream tools (edit/enhance/virtual_try_on/video) receive a URL and activate the `url` input node. No type distinction or conversion.
- **Auto-detection in the consuming tools**: they already implement `urlparse` — if they receive a URL they activate `source="url"`; if they received a filename they would activate `source="temp"`. By always emitting a URL, `url` is always used.
- **Note on persistence**: it is **assumed** that everything is temporary by design (own custom node; nothing is saved in `output`). The URL points to temporary files just like the filename; the URL is chosen for consistency with the comparator, **not** for persistence. It is not a pending restriction.

## 6. SEPARATE NOTE — Size of the video embed (pending decision)

Unlike the image, the **video has no zoom viewer** (there is no "click to see bigger"). Therefore, the video embed is the **only view** the user will have, and it must be decided how much space it uses:

- **Options**:
  - **(A)** Use all the available area: height limited to the viewport area, without a restrictive cap. The video fills the maximum that fits without overflowing, in both vertical and horizontal.
  - **(B)** Intermediate cap (e.g., 70vh, like the image): large but without dominating the chat, assuming there is no zoom.
  - **(C)** Prioritize maximum width + proportional height (like the slider): adapts by aspect, large horizontal / tall but proportional vertical.
- **Common technical requirement**: container with height limited to the available area (viewport unit) + `object-fit: contain` + `max-width`/`max-height` 100% + centered → adapts to vertical and horizontal screens **without overflowing the height**, and `reportHeight()` keeps the iframe at the real height.
- **Question to resolve**: how much should the video "use the available area", given that it has no zoom.

> **Status: DECISION PENDING.** This is the last component to be tackled in the plan; the decision (A/B/C) is recorded here when it is made.

## 7. Distinct internal domains and CORS

The images generated by ComfyUI hang from an **internal TLD different** from Open WebUI's (both internal services, port 80, HTTP). The user **controls both reverse proxies**.

### Communication and CORS

- **Cross-origin** affects the **reading** of the image (forced download with `fetch(blob)`), not its display (the `<img>` does not need CORS).
- For the modal's **download button** to work with a **forced download** inside the iframe, ComfyUI must authorize the Open WebUI origin via CORS.
- **Both HTTP** → no mixed content → images load without being blocked in the `<img>`.
- `allowSameOrigin` remains **OFF** (security does not change due to the ComfyUI cross-origin).
- **Decision (2026-08-04)**: proceed with `Access-Control-Allow-Origin: *` (allow-all) on the ComfyUI proxy. A same-origin proxying route through the Open WebUI proxy was considered and **parked** as too complex; CORS/security tuning is out of scope for now.

### Configuration in the ComfyUI proxy

The **ComfyUI proxy** must respond:

| Request | Who responds | Headers |
|---------|--------------|---------|
| **`OPTIONS` (preflight)** | **The proxy** | `200` + `Access-Control-Allow-Origin` + `Access-Control-Allow-Methods: GET, OPTIONS` + `Access-Control-Allow-Headers: *` |
| **`GET` (actual image)** | ComfyUI (via proxy) | — |

- The **`OPTIONS` preflight must be answered by the proxy** (not ComfyUI), returning `200` + CORS headers.
- `Access-Control-Allow-Origin`: Open WebUI origin (or `*`). No credentials, so `*` is compatible.
- `Access-Control-Allow-Headers: *` is acceptable in this context (internal services, local/VPN network). If some browser fails with `*` in `Allow-Headers`, list the headers explicitly.
- **No additional configuration is needed in the Open WebUI proxy** for this flow (it only serves the embed HTML, same origin).

### Forced download (what it is)

- It is using JS to **force** saving the file: `fetch(blob)` → `URL.createObjectURL` → trigger a download with the `download` attribute.
- It ignores the server's `Content-Disposition` (inline vs attachment).
- **Requires CORS** (because of the blob `fetch`). Without CORS, the alternative would be opening the image in a new tab (the browser shows it and the user saves it manually), which does not require CORS.

## 8. Review of the native Open WebUI viewer (research)

To try to replicate the appearance of the Open WebUI lightbox, the frontend was explored:

- It is **not** a separate modal component (`ImageModal` does not exist as such); the image rendering lives inside the chat's Markdown/Output system.
- Relevant files located:
  - `src/lib/components/chat/Messages/Markdown.svelte` — thin wrapper.
  - `src/lib/components/chat/Messages/ContentRenderer.svelte` — orchestrates content rendering (manages artifacts/embeds: `showArtifacts`, `showEmbeds`, `FloatingButtons`).
  - `src/lib/components/chat/Messages/MarkdownTokens.svelte` and `Markdown/MarkdownInlineTokens.svelte` — image tokenization/rendering.

## Appendix A — Verification against the Open WebUI source code

The assumptions in this document were verified against `open-webui/open-webui` (`main`) rather than relying only on the official docs.

### A.1 Middleware — `backend/open_webui/utils/middleware.py`, `process_tool_result()`

- **Tuple support confirmed**: `(HTMLResponse, context)` with `len == 2` and the first element an `HTMLResponse` is unpacked; if the second element is a `str`, `dict`, or `list`, it is sent to the LLM. Otherwise (including "no second element"), the LLM receives the generic message:
  `{ "status": "success", "code": "ui_component", "message": "<tool_name>: Embedded UI result is active and visible to the user." }`
- **`Content-Disposition: inline`** is required for the body to be treated as an embed; otherwise the HTML is passed through as plain text.
- The HTML body is emitted via the **`embeds`** event (`{"type": "embeds", "data": {"embeds": [...]}}`).
- Non-2xx status codes on the `HTMLResponse` produce an error message instead of the context.
- **`image_md` has no special handling** in the middleware: it is plain text that enters the LLM context and relies on the agent reproducing it. This confirms the hack and the motivation for eliminating it.
- **Implementation consequence for "empty context"**: returning the bare `HTMLResponse` (no tuple) makes the LLM receive the generic message above. An *empty dict* `{}` is a valid `dict`, so it **would** be sent to the LLM as context — do not use `{}` for terminal tools.

### A.2 Frontend — `src/lib/components/common/FullHeightIframe.svelte`

- **Sandbox flags**: `allow-scripts`, `allow-popups`, `allow-downloads` are always on; `allow-same-origin` and `allow-forms` are off unless the user enables them in Settings → Interface. Confirmed in `ToolCallDisplay.svelte` (`iframeSandboxAllowSameOrigin ?? false`, `iframeSandboxAllowForms ?? false`). This validates the security decision in the common pattern.
- **Height reporting**: the component listens for `{ type: 'iframe:height', height: number }` postMessages and sets `iframe.style.height`. **No initial height is set**, so the iframe starts at the browser default (~150px) until the first height report → every embed must call `reportHeight()` on `load` and re-report on content changes (image/video load, resize) to avoid the visible "jump".
- **CSP injection**: the HTML is passed through `injectCsp(iframeDoc, $config?.ui?.iframe_csp ?? '')` before being set as `srcdoc`. Inline styles are not affected by Open WebUI's default embed CSP, but this is worth knowing if the embed grows.
- **Placement and persistence**: tool embeds render inline at the tool-call indicator ("View Result from `<name>`"), are **not collapsible**, and are **persisted in chat history** (not ephemeral).
- **`window.args`**: injected only when `allowSameOrigin` is on. With the sandbox OFF (our case) it is `undefined` — not needed by this design, but any future embed must not rely on it.

### A.3 Downloads

- `allow-downloads` is enabled in the iframe component by default, but the official docs warn that sandboxed iframes on **iOS** cannot reliably trigger file downloads. The fallback (open the image in a new tab) is already part of the design. `allow-popups` is also enabled by default, so `window.open`/anchor targets work.

## Appendix B — Implementation notes / considerations

- **Shared viewer HTML**: each tool in this repo is a standalone script pasted into Open WebUI (no shared package at runtime), so the image-viewer HTML will be **duplicated** inside each tool that needs it. Keep the markup/JS byte-identical across tools and update all copies together to avoid drift.
- **Aspect ratio known a priori**: `smart_generate_image` computes `reduced_w:reduced_h` and can reserve the aspect ratio to avoid the load "jump". `edit_image`, `enhance_image`, and `virtual_try_on` do **not** know the output dimensions in advance (they depend on the input image), so their viewers must rely on `reportHeight()` after the image loads instead of aspect reservation.
- **`reportHeight()` contract**: report on `window.load`, on image/video `load` events, on `resize`, and via a `ResizeObserver` on the body — the parent iframe starts at ~150px and only grows when a message arrives.
- **URL escaping**: image/video URLs contain query strings (`?filename=...&type=...`); they must be HTML-escaped before being injected into `src` attributes (already the practice in `compare_images`).
- **`generate_caption` is out of scope**: it returns plain text (a caption), not an image; it is not part of this migration.
